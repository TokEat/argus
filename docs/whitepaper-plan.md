# Argus 技术白皮书规划稿

> 本文档用于规划 Argus 项目的正式白皮书，不直接替代白皮书正文。
>
> 目标是先统一“为什么写、写给谁看、讲什么、怎么讲、用什么证据讲”，再进入正式撰写阶段。

---

## 1. 白皮书定位

建议白皮书名称：

- 《Argus 分布式攻击面管理与漏洞巡航平台技术白皮书》

建议副标题：

- 从单机扫描工具到企业级分布式 ASM 控制面的架构演进与实践

白皮书定位建议：

- 对外：用于介绍 Argus 的技术路线、平台能力、架构设计、适用场景与落地价值
- 对内：作为统一的项目叙事底稿，减少 README、架构文档、汇报材料之间的重复和口径漂移

它不应只是“功能清单”，而应回答这四个问题：

1. Argus 要解决什么问题
2. Argus 为什么采用当前架构
3. Argus 当前已经做到什么程度
4. Argus 后续将如何演进

---

## 2. 目标读者

建议把读者拆成三层，否则白皮书容易失焦：

### A. 技术决策者

- 安全负责人
- 研发负责人
- 平台架构师

他们关注：

- 为什么要用分布式
- 为什么不是简单把扫描工具堆在一起
- 平台的扩展性、稳定性、治理能力如何

### B. 一线使用者

- 安服工程师
- 红队 / 蓝盾 / 漏洞运营人员
- 平台运维人员

他们关注：

- 平台能做什么
- 任务如何下发
- 规则如何管理
- 节点如何运行

### C. 项目参与者

- 开发者
- 新加入成员
- 后续维护者

他们关注：

- 当前系统边界在哪里
- 哪些能力已经落地
- 哪些是设计中、哪些是未完成

---

## 3. 白皮书写作目标

建议正式白皮书同时完成以下目标：

- 统一项目对外叙事，不再让 README 承担“半白皮书”角色
- 解释控制面 / 数据面的设计动机，而不是只陈述目录结构
- 讲清楚 Argus 的核心链路：任务、规则、节点、结果
- 明确当前实现边界，避免把“规划中能力”写成“已交付能力”
- 给后续版本演进留出清晰路线

不建议白皮书承担的内容：

- 逐行接口说明
- 全量 API 手册
- 纯开发者内部的函数级设计
- 临时状态说明

这些应继续由现有文档承担：

- `docs/interface-implementations.md`
- `docs/implementation-status.md`
- `docs/project-structure.md`

## 4. 推荐白皮书结构

下面这套结构适合 Argus 当前阶段，既能对外讲清楚，也不会和现有文档重复太多。

### 第一章：项目背景与问题定义

目标：

- 说明 ASM / 分布式漏洞巡航的现实问题
- 说明单机式工具在企业场景下的边界
- 引出 Argus 的平台化必要性

建议回答：

- 为什么单机 CLI 在资产规模扩大后会失效
- 为什么需要控制面与数据面分离
- 为什么规则、任务、结果要中心化治理

### 第二章：Argus 的平台定位

目标：

- 给出 Argus 的一句话定位
- 说明平台核心能力边界

建议写法：

- Argus 是一个“分布式攻击面管理与漏洞巡航平台”
- 它兼容单机 CLI，但核心价值在于平台化、分布式、规则中心化、结果聚合化

建议输出：

- 平台能力图
- 典型使用场景表

### 第三章：总体架构设计

目标：

- 讲清楚控制面、数据面、协议层、规则中心、存储层的关系

建议包含：

- 总体架构图
- 控制面职责
- 数据面职责
- PostgreSQL / RabbitMQ / gRPC / Web Console 的作用边界

建议重点：

- 为什么调度走 RabbitMQ 多优先级队列
- 为什么结果拆成资产 / 指纹 / 漏洞三层
- 为什么规则要中心化

### 第四章：核心业务闭环

目标：

- 用流程而不是模块清单解释系统

建议拆成四条主线：

1. 任务闭环
   - 创建任务
   - 目标标准化
   - RootTask / SubTask 拆分
   - 入队 / 调度 / 执行 / 完成

2. 节点闭环
   - 注册
   - 心跳
   - 掉线识别
   - 任务回收

3. 规则闭环
   - 导入
   - 审批
   - Manifest
   - Agent 同步
   - 回滚

4. 结果闭环
   - 流式回传
   - 异步缓冲
   - 三层落库
   - 查询 / 导出 / 展示

### 第五章：关键技术设计

目标：

- 把“有说服力的技术选择”讲透

建议包含：

- RabbitMQ 多优先级调度模型
- gRPC 通信设计
- BatchWriter 防洪落库
- Arsenal 与结构化规则表双层设计
- 多租户与 RBAC 的当前做法

这章是白皮书的技术含量核心，建议重点写。

### 第六章：前端控制台与运营能力

目标：

- 说明平台不是只有后端和 Agent

建议包含：

- Dashboard
- 任务管理
- 节点管理
- 结果查看
- 画像查询
- 规则管理

注意：

- 对“CloudManagement / RoleManagement / Build”这类链路未闭环能力，要明确写成“在建 / 部分实现”，不要写成成熟功能

### 第七章：当前实现状态与边界

目标：

- 用白皮书语言引用当前真实状态
- 保持可信度

建议聚焦：

- 已完成能力
- 已有代码但未闭环能力
- 明确尚未完成能力

这一章应和 `docs/implementation-status.md` 保持一致，但表达更偏对外。

### 第八章：典型落地场景

目标：

- 帮读者建立“怎么用”的直觉

建议包含：

- 红队外网资产巡航
- 安服批量漏洞排查
- 企业多节点定期巡检
- 规则中心化治理

### 第九章：演进路线图

目标：

- 合理表达未来方向，而不是画大饼

建议路线：

- 近端：
  - 打通 Agent 鉴权链路
  - 修复 Cloud / Build 假接口
  - 完善 RootTask 终态收敛
- 中期：
  - 节点容量与标签调度
  - 遥测日志链路
  - Clean Architecture 迁移
- 远期：
  - 真实云资源编排
  - 容器隔离执行
  - 真实 LLM 审查与运营能力

## 6. 正式白皮书的写作原则

建议统一遵循以下原则：

### 原则一：讲动机，不只讲功能

避免只写：

- “支持任务管理”
- “支持规则同步”

要写成：

- 为什么任务需要拆分
- 为什么规则需要中心化
- 为什么结果需要分层存储

### 原则二：区分“已实现”和“规划中”

Argus 当前最容易出现的问题，不是功能太少，而是文档太容易把“代码存在但没接线”的内容写成“已完成”。

白皮书里建议统一使用三类表述：

- 已落地主链路
- 已有实现基础，正在闭环
- 规划方向

### 原则三：优先画清楚主链路

如果读者读完整份白皮书，只记住一件事，那应该是：

- Argus 如何从“任务输入”走到“规则执行”和“结果聚合”

### 原则四：图比堆字更重要

建议至少准备 4 张图：

1. 总体架构图
2. 任务流转图
3. 规则同步图
4. 结果回传与落库图

## 8. 推荐成稿节奏

如果我们要把正式白皮书写出来，建议按四步推进：

### Step 1：先定目录与口径

产出：

- 这一份规划稿

### Step 2：先写“不会变”的章节

优先写：

- 项目背景
- 平台定位
- 总体架构
- 核心业务闭环

这些章节最稳定，也最容易统一口径。

### Step 3：再写“和当前实现强相关”的章节

补写：

- 当前实现状态
- 前端控制台
- 典型场景
- 演进路线

### Step 4：最后补图、术语表和对外摘要

这样可以避免一开始就在排版和修辞上消耗太多时间。
